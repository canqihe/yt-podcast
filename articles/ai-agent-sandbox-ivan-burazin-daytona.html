核心要点

01

沙箱即刚需

智能体是数字知识工作者，需要独立、安全、有状态的计算环境。不只是运行代码，更是安全隔离和权限管控的基石。

02

状态是分水岭

传统云为无状态应用设计，智能体需要长时间运行的有状态环境。两者架构根本不同——卡车和跑车的区别。

03

技术三明治架构

沙箱 = 基础设施（60ms 启动、70 秒 5 万并发）+ 原语（Firecracker/QEMU/容器）+ 工具（辅助 + 护栏），统一接口交付。

04

自建是陷阱

启动一个 Firecracker 很简单，启动一百万个、加功能、保吞吐量和安全性——每一步都是数量级的复杂度跳跃。

05

GPU 之后是 CPU

强化学习崛起和智能体规模化，正在制造一个被忽视的 CPU 短缺危机。GPU 越强大，需要「喂养」它的 CPU 沙箱越多。

06

支持即增长

Daytona 零销售人员，通过极致客户支持构建增长引擎：快速首次响应 + 明确承诺 + 主动更新。是纪律，不是技术。

01

智能体为什么需要自己的电脑？

00:00 - 03:20
核心观点

智能体就是「数字知识工作者」——正如人类知识工作者需要电脑来完成复杂工作，智能体同样需要自己的计算环境，而沙箱就是它们的办公电脑。

深度阐述
安全底线

Ivan 分享了一个亲身经历：在准备董事会报告时，他让 Claude 去获取银行数据。Claude 的回复是「你登录一下，给我权限就行了」。这个瞬间让他意识到：让智能体直接访问主计算环境，从根本上就是不安全的。

数字员工方案

他的解决方案是给智能体一个独立的 Daytona 沙箱账户、一个独立的手机号（用于银行双重验证）、严格限制的账户权限（只能查看银行数据，不能转账），以及一张日限额 100 美元的信用卡。这样即使智能体「失控」，最坏也只是数据泄露而非资金损失。

Open Claw 的类比

Open Claw 的 Mac Mini 实验让很多人第一次理解了沙箱的概念——Mac Mini 就是那个沙箱，只不过 Daytona 把它做成了云端可扩展的基础设施。

「我把智能体看作数字知识工作者。我的观点是，每个智能体至少需要一个沙箱，有时需要更多。」— Ivan Burazin [00:00:00]
02

传统云为什么不适合智能体？

05:17 - 07:04
核心观点

超大规模云服务商（AWS、Azure、GCP）是为无状态应用部署而设计的，而智能体需要的是有状态、长时间运行的计算环境——两者在架构上根本不同。

深度阐述
卡车 vs 跑车

传统云像卡车——重量大、底盘稳、为缓慢但安全地运输货物而设计。你部署一个应用（如 eBay 页面更新），不希望它被动态修改。整个云架构围绕「无状态」设计。智能体沙箱像跑车——同样有引擎和轮子，但追求极致速度、弹性和动态变化。

localhost 的终结

CodeSandbox 十年前就使用了微虚拟机、快照、分叉等技术，但那时给人类开发者的价值不够大。开发者说了 20 年「你只能从我冰冷的手中夺走我的 localhost」。直到智能体出现才真正推动了从本地到云端的迁移——因为智能体需要并发能力、不间断运行和远程访问。

「你可以用卡车和跑车都做很多事情，但它们在根本上是不同的东西。」— Ivan Burazin [00:06:55]

智能体栈全景：六大核心组件

14:10 - 16:32
核心观点

Ivan 将智能体栈拆解为模型（大脑）、工具（手脚）、记忆（经验）、编排（管理）、可观测性（监督）和沙箱（工作台）六大组件——大部分并非全新发明，而是现实工作方式的数字化映射。

深度阐述
六大组件

模型=大脑（理解、推理、生成），工具=手脚（MCP、工具调用、沙箱），记忆=经验（目前最好的方案是 Markdown 文件），编排=管理（管理智能体与管理人类并无太大不同），可观测性=监督（验证工作质量），沙箱=工作台（完整计算环境）。

模型不会学习

Ivan 指出了最令人困扰的挑战：当前模型实际上不会「在工作中学习」。即使解决了记忆问题——模型有上下文、有历史——它仍然不会从昨天的经验中变得更聪明。你做同一件事五次，它第六次可能还是犯错。这是否需要持续的强化学习后训练？还是需要模型架构的根本改变？目前没有明确答案。

「和一个不会变聪明的『同事』工作，感觉很奇怪。你做某件事五次，它第六次还是会搞砸。」— Ivan Burazin [00:18:20]

沙箱的技术三明治：基础设施 + 原语 + 工具

40:50 - 46:09
核心观点

Daytona 将沙箱拆解为三层架构——基础设施（启动速度、并发能力、规模）、原语（隔离形态）、工具（辅助+护栏）——并通过统一接口提供给用户。

深度阐述
基础设施层

单个沙箱启动时间 60 毫秒。70 秒内启动 5 万个。有客户每天运行数十亿个。为什么速度关键？对于 RL 训练，GPU 是最贵的资源，必须保持 100% 利用率。沙箱（CPU 机器）按批次启动执行任务，启动越快 GPU 空转时间越短。有客户要求 500 万并发。

原语层

Daytona 是目前唯一支持多种隔离形态的沙箱提供商：Firecracker（快速精简，但不能 GPU）、QEMU/Cloud Hypervisor（近乎完整虚拟机，可支持 GPU 和 Android 模拟）、Docker+Sysbox（高密度加固）。用户不需要知道底层用了什么——「我需要 Windows」就启动对应形态。还能运行中动态调整规格——智能体用满资源时系统自动扩展而非崩溃。

工具层

辅助工具（无头终端、文件操作——用更少 token 更快完成工作）和安全护栏（密钥管理器、防火墙——防止智能体做蠢事）。

「我们对沙箱的看法是——计算资源消费的人体工程学。」— Ivan Burazin [00:41:05]

深度阐述

更令人兴奋的是探索能力。智能体可以在决策点拍快照，然后继续走一条路（失败就回滚），或者复制沙箱同时尝试多条路径。这是人类无法做到的事——我们只能在一条时间线上前进，但智能体可以「分身」。

「智能体可以复制沙箱，同时尝试两条路径。显然可以更多。」— Ivan Burazin [00:51:20]

为什么 Daytona 从零重写调度器

51:40 - 55:25
核心观点

Kubernetes、Nomad 等现成调度器不是为「超快启动+有状态+长时间运行」的工作负载设计的。Daytona 从零构建的自定义调度器不仅带来性能优势，还赋予了多云灵活性和多隔离形态支持。

深度阐述
三个原因

第一，Kubernetes 不是为毫秒级启动、秒级扩展到数万、频繁创建销毁的场景设计的。第二，沙箱不应该默认短暂——就像你的笔记本电脑，你想让它一直工作到任务完成。第三，有状态沙箱需要实时迁移——底层服务器也需要维护（重启、打补丁），你必须能在服务器之间迁移沙箱不让用户感知中断。

额外收益

多云灵活性：调度器可连接任何 CPU 机器，让它成为 Daytona 云的一部分。类似 Base10 和 Fireworks，在多个计算提供商上运行避免锁定。多形态支持：自动根据用例选择 Firecracker、Cloud Hypervisor 或容器。

「我们非常天真地发现这些东西不好用。没有一个是为超快、有状态、长时间运行的机器设计的。」— Ivan Burazin [00:53:17]

长时间运行沙箱的隐藏挑战

55:24 - 58:12
核心观点

让沙箱长时间运行不只是性能问题，而是系统管理难题——你必须解决实时迁移，否则永远无法维护底层服务器。

深度阐述
问题的根源

云计算的「弹性」只是消费端体验。总得有人实际把服务器拧在一起、开机、确保它能工作。如果沙箱默认短暂（Lambda 函数运行 5-10 分钟），底层维护很简单——设个「不可调度」标志，等沙箱自然结束再维护。但如果沙箱需要运行几天甚至几周，就必须能在不中断的情况下维护底层服务器。

商业数据

只有 2.5% 的沙箱运行超过 24 小时，但贡献了 20% 的收入——长时间运行意味着持续计费。有些用户反而要求短暂——运行完毕后所有数据彻底销毁，适用于高安全场景。

「即使技术消费者也会觉得『所有计算都是弹性的』——是的，你从 AWS 消费是弹性的，但总得有人实际把服务器拧在一起。」— Ivan Burazin [00:57:00]

自建沙箱的陷阱

58:10 - 01:01:06
核心观点

「我可以在一台机器上启动一个 Firecracker」——是的。但启动一百万个、添加所有功能、保证吞吐量和安全性——那完全是另一个量级的问题。

深度阐述
本地硬盘 vs 网络存储

Daytona 最重要的技术决策之一是使用本地硬盘而非网络存储。行业常规是 CPU+内存用本地的，硬盘用网络驱动器（管理简单，服务器死了数据还在共享驱动器上）。但 IOPS 差距是数量级的：网络驱动器几十万，本地驱动器几千万——100 倍差距。当智能体需要高速磁盘操作时，这是「能用」和「不能用」的分界线。

自建演进陷阱

典型路径：阶段一「只需要运行代码」——Docker 就行；阶段二规模增长——管理大量沙箱碰壁；阶段三性能需求出现——需要高速磁盘操作；阶段四回头找 Daytona——「实际上我们现在做不了 X 和 Y 了」。

「你可以启动一个 Firecracker，但启动一百万个就是问题了。」— Ivan Burazin [00:58:41]

CPU 短缺：下一个全球计算危机？

01:01:03 - 01:02:49
核心观点

SemiAnalysis 报告指出 CPU 可能即将耗尽。原因：强化学习是模型进步的最大引擎需要大量 CPU 机器，GPU 越强大需要越多 CPU「喂养」，而智能体规模化意味着数百万 CPU 实例。

深度阐述
三个被忽视的驱动因素

第一，过去 18-20 个月模型能力的最大提升来自 RL 训练，而 RL 需要大量 CPU 沙箱作为环境。第二，新一代 GPU 可以并行处理更多任务，每个 GPU 需要更多 CPU 沙箱——需求不是此消彼长而是同步增长。第三，如果每个智能体至少需要一个沙箱，数百万智能体就意味着数百万 CPU 实例。

Daytona 的应对

Daytona 也感受到了压力——有客户要求 500 万并发 CPU 沙箱。通过自定义调度器的多云灵活性来应对，可以连接任何计算提供商来扩展容量。

「GPU 更强大了，它们可以并行处理更多 CPU 机器。然后你看看 Intel 的股价就知道了。」— Ivan Burazin [01:01:50]

当前智能体栈的所有设计都建立在 Transformer 之上。如果出现根本性的模型架构变革，整个基础设施层可能需要重新设计。

Daytona：智能体基础设施的先行者

从 2009 年开创云端 IDE 到今天构建智能体沙箱基础设施，Ivan Burazin 和他的团队走过了 16 年的创业之路。他们的核心洞察是：智能体需要的不是传统云的一小部分，而是一种全新的计算范式——有状态、可扩展、安全隔离的「可组合计算机」。

「60 毫秒启动一个沙箱，70 秒启动 5 万个，每天运行数十亿个——这不是未来，这是现在正在发生的事。」
